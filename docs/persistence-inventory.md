## Identity dependencies

- **Exact workflow integrity and historical provenance.** Recipe/SDK bytes → publication digest → Host request digest and accepted snapshot → planner ManifestHash → runner checkpoint/report → recovery, history and artifact validation. Preserve the legacy value across those edges.
- **Logical documents.** Document kind, schema and codec identifiers domain-separate DocumentId. The catalog binds it to a physical BlobId and optional official CanonicalDigest. No RPC legacy SHA field becomes a DocumentId.
- **Source and environment.** Source snapshot ID, environment-lock SHA, variant/kit locks, dependency inputs and the toolchain fingerprint bind distinct policy domains. The manifest carries these values unchanged.
- **Approval.** Provisioning policy and resolved plan, dependency approvals, and remote experiment stage approval authorize different actions. Migration equivalence has no authority to create or reinterpret approval.
- **Execution.** Request digest, operation ID, workspace identity, selection, result reservation and dispatch/checkpoint evidence decide execution lifecycle. A canonical manifest is only one input.
- **Cache.** An action key includes independently versioned effective execution inputs. A physical digest addresses the output. Adoption must not turn logical identity equality into a cache hit.

## Native execution follow-on

- The workflow and resolved execution plan share the production execution-document CAS. Binary ledger epoch 3 binds the exact authorized plan DocumentId and a separately versioned dispatch identity. Earlier ledgers continue to use the inline binding.
- Source request identity binds the Lore snapshot. Recovery reopens the workflow and plan then verifies the operation-owned materialization before dispatch. Source storage and IDs retain their existing contract.
- The managed tooling store owns binary environment locks and vcpkg receipts under format-scoped identities. A vcpkg receipt contains its approved dependency plan and a separate first-receipt pin. Tooling plans are caller-owned immutable files checked against the current provisioning plan before applying. Execution CAS collection uses the existing shared lease and retention table for workflow and plan roots.
- The checkpoint, History evidence, Action Cache metadata and report projections retain their formats. Further verification and deployment decisions are tracked in [ADR-0009](adr/0009-binary-workflow-execution.md) and the [P4 verification report](p4-binary-execution-verification.md).
